# issue-rule.md

## Issue Documentation Rules

---

## 1. 이슈의 기본 관점 및 원칙

이 프로젝트에서 이슈(Issue)는 AI가 작업을 진행하는 과정에서 **스스로 판단할 수 없는 문제를 사용자에게 위임하기 위한 공식 기록 수단**이다.

이슈는 문제 해결을 위한 토론 공간이 아니라 **판단 보류 상태를 명확히 남기기 위한 로그**로 취급한다.

### 1.1 이슈의 목적

- 이슈는 다음과 같은 상황을 기록하기 위해 존재한다.
  - 문서 간 규칙 충돌
  - 문서 정의의 누락 또는 모호성
  - 구현을 계속하기에 판단이 필요한 설계 문제
  - 규칙 위반 가능성이 있는 요구사항
- AI는 이슈를 통해 문제를 기록하고 위임하되, 임의로 문서를 수정하거나 판단을 대신하지 않는다.

### 1.2 이슈와 작업 진행의 관계

- 이슈가 기록되었다는 사실만으로 작업이 중단되지는 않는다.
- AI는 문제의 영향 범위를 식별하고, 문제가 되는 기능 또는 동작을 제외한 범위에서 작업을 계속 진행한다.
- 어떤 방식으로 작업을 지속했는지는 이슈를 통해 사용자에게 명확히 전달되어야 한다.

### 1.3 작업 중단 원칙

다음 조건 중 하나라도 충족되면, AI는 작업을 중단하고 사용자 판단을 요청한다.

- 규칙 문서 간 충돌로 인해 올바른 동작을 결정할 수 없는 경우
- 데이터 손실 또는 보안 문제로 이어질 가능성이 있는 경우
- 프로젝트가 정상적으로 빌드 또는 테스트될 수 없는 상태가 되는 경우

### 1.4 AI의 제한 사항

- AI는 이슈를 기록할 수 있으나, 이슈를 근거로 문서나 규칙을 직접 수정하지 않는다.
- 이슈에 대한 최종 판단과 문서 반영은 항상 사용자의 책임이다.

---

## 2. 이 문서의 역할

이 문서는 `/docs/issues/` 디렉토리 내에서 관리되는 **이슈(Issue) 문서**를
어떻게 작성·추적·종결(Resolved)하는지에 대한 **운영 규칙**을 정의한다.

- 이슈의 관점/철학(왜 기록하는가, 작업을 멈출지 등)은 `00-overview.md`에서 정의한다.
- 본 문서는 **형식, 필드, 생명주기, 추적 규칙**만을 정의한다.
- 실제 이슈 파일은 본 문서의 규칙을 반드시 준수해야 한다.

---

## 3. 이슈 문서의 구성 원칙

### 2.1 파일 단위 원칙

- 하나의 이슈는 **하나의 파일**로 기록한다.
- 하나의 파일에 여러 이슈를 기록하지 않는다.
- 이슈 파일은 **생성(Create)** 을 원칙으로 하며, 기존 이슈 파일의 내용 수정은 허용하지 않는다.
  - 단, 사용자가 필요에 따라 별도의 후속 이슈 파일을 생성하는 것은 허용된다.

### 2.2 실행 단위 기준

- 이슈는 **실행 단위 기준**으로 기록한다.
- 실행 단위 예시:
  - 특정 Step 실행 중
  - 특정 PR 생성 과정 중
  - 특정 테스트/빌드 실행 중
- 실행 단위가 다르면 동일한 문제라도 **별도의 이슈 파일**로 기록한다.

---

## 4. 이슈 파일 네이밍 규칙

이슈 파일명은 다음 형식을 따른다.

```
ISS-YYYY-MM-DD-HHMM-[context].md
```

- `YYYY-MM-DD-HHMM`은 기록 시점 Timestamp이며 **Asia/Seoul 기준**이다.
- `[context]`는 실행 단위를 식별하는 최소 문자열이다.
  - 예: `step03`, `pr-12`, `build`, `test-login`

예시:

```
ISS-2026-01-23-1310-step03.md
ISS-2026-01-23-1422-pr-12.md
```

---

## 5. Timestamp 작성 규칙

- 모든 이슈 파일에는 Timestamp를 반드시 포함한다.
- Timestamp는 **Asia/Seoul 기준**이며, 다음 형식을 **엄격히** 따른다.

```
YYYY-MM-DD HH:MM
```

- ISO 변형, 상대 시간, 다른 시간대 표기는 허용하지 않는다.

---

## 6. 작성 언어 규칙

- 이슈 파일의 **설명(본문)** 은 단일 언어로만 작성한다.
- 프로젝트에서 기본 언어가 지정되지 않았다면 기본값은 **한국어**다.
- 하나의 이슈 파일 내에서 언어를 혼합하지 않는다.
- 단, 상태값(Status)은 본 문서에서 정의한 **영어 고정 값**만 사용한다.

---

## 7. Template 문서와의 관계

- 실제 이슈 파일은 템플릿을 복사하여 생성하는 것을 원칙으로 한다.
- 이슈 파일의 정확한 기본 구조는 `/docs/issues/template.md`를 따른다.
- 템플릿과 본 문서가 충돌할 경우 **본 문서가 우선**한다.

---

## 8. Issue ID 및 생명주기 규칙

### 7.1 Issue ID 고정 원칙

- 모든 이슈는 파일명과 별개로 **고유 Issue ID**를 반드시 가진다.
- Issue ID는 이슈의 생명주기를 추적하는 기준이며, 프로젝트 내에서 절대 중복될 수 없다.

**형식(고정)**

- `IID-0001` (4자리 0-padding)
- 예: `IID-0001`, `IID-0002`

---

### 7.2 Status(상태) 값 규칙 (영어 고정)

- 모든 이슈 파일에는 `Status`를 반드시 포함한다.
- Status는 다음 값 중 하나만 허용한다. (영어 고정)

- `Open`
- `Addressed`
- `Resolved`

---

### 7.3 지속 언급(Chaining) 규칙

- 한 번 `Open`으로 기록된 Issue ID는, `Resolved` 되기 전까지 **반드시 추적**되어야 한다.
- 이를 위해, 새 이슈 파일에는 현재 시점의 **미해결 Issue ID 목록**을 포함해야 한다.
  - (템플릿의 `Open Issues` 섹션을 사용)
- 미해결 Issue ID를 누락하면 규칙 위반으로 간주한다.

---

### 7.4 Resolve(해결) 기록 규칙

- 이슈는 기존 파일을 수정해서 해결 처리하지 않는다.
- 해결 확정은 **후속 이슈 파일(새 파일)** 로 기록한다.
- 해결 확정 파일은 다음 조건을 만족한다.
  - 동일 `Issue ID`를 사용한다.
  - `Status: Resolved`를 사용한다.
  - 상단 요약 영역에 다음 필드를 포함한다.
    - `Resolved At`
    - `Resolution Summary`

**Resolved At 규칙**

- `Resolved At`에는 해결이 확정된 시점을 대표하는 **이슈 파일명(ISS-...md)** 을 기록한다.
- 예: `ISS-2026-01-23-1422-step03.md`

---

### 7.5 Resolved 파일의 본문 최소화 규칙

- `Status: Resolved`인 이슈 파일은 **이슈 관리 목적**을 우선한다.
- 따라서 해결된 이슈 파일은 다음 정보만을 **파일 최상단 요약 영역에** 기록하는 것을 원칙으로 한다.
  - `Issue ID`
  - `Status`
  - `Resolved At`
  - `Resolution Summary`

- 해결 이전의 세부 맥락이 필요하면, 과거 이슈 파일(Open/Addressed)을 참조한다.
- 단, 프로젝트 운영상 필요하다고 판단될 때만 제한적으로 추가 정보를 포함할 수 있으며,
  이 경우에도 요약 영역은 반드시 최상단에 유지한다.

---

## 9. Label(항목) 규칙

### 8.1 Label 고정 원칙

- 이슈 파일은 템플릿이 정의한 Label 집합을 사용한다.
- Label 이름(헤더)은 변경할 수 없다.
- Label 이름은 영어로 고정하며, Label 아래 설명은 5장의 언어 규칙을 따른다.

---

## 10. 규칙 위반 처리

- 본 문서 규칙을 따르지 않은 이슈 파일은 유효한 이슈로 간주하지 않는다.
- 규칙 위반이 발견되면, 별도의 새 이슈 파일로 이를 기록한다.

---

## 11. 이 문서의 위상

이 문서는 `/docs/issues/` 디렉토리 내에서 **이슈 작성·추적·종결 규칙의 최상위 문서**다.

---

## 12. 로그 디렉토리 분리 규칙 (추가)

### 11.1 디렉토리 구조

이슈 문서는 다음 구조를 따른다.

```
/docs/issues
 ├─ issue-rule.md        ← 이슈 규칙 (본 문서)
 ├─ template.md          ← 실행 단위 이슈 로그 템플릿
 ├─ README.md            ← 실행 결과 요약 리포트 (자동 생성 가능, 파생 문서)
 ├─ readme-template.md   ← README 고정 포맷 템플릿(규범)
 └─ logs/
     └─ ISS-YYYY-MM-DD-HHMM-[context].md
```

- 실제 실행 단위 이슈 로그 파일은 반드시 `/docs/issues/logs/` 하위에 생성한다.
- `/docs/issues/` 루트에는 규칙 문서, 템플릿, 요약/포맷 문서만 위치한다.
- 위 규칙을 위반한 이슈 파일은 유효한 이슈 로그로 간주하지 않는다.

---

## 13. issues/README.md 자동 생성 및 고정 포맷 (추가)

### 12.1 README의 성격

- `README.md`는 `/docs/issues/logs/` 하위 로그를 기반으로 한 **요약 리포트(derived artifact)** 다.
- README는 기준 문서(Source of Truth)가 아니다.
- 기준 문서는 항상 `/docs/issues/logs/ISS-*.md` 이다.
- README는 언제든 삭제될 수 있으며, 필요 시 다시 생성된다.

### 12.2 README 생성 주체 및 권한

- AI는 실행 종료 시 `README.md`를 **자동 생성/갱신**할 수 있다.
- README의 내용은 결정(Decision)이나 규칙 변경으로 간주되지 않는다.
- README는 요약 용도이며, 사용자 판단을 대체하지 않는다.

### 12.3 README 생성 시점

- 하나의 실행 세션 종료 시
  - 예: Preflight 완료 후 Step 실행 완료, 테스트 통과, PR 생성 완료 등
- 또는 사용자가 명시적으로 요약 생성/갱신을 요청한 경우

### 12.4 README 고정 포맷(규범)

- README의 고정 포맷은 `/docs/issues/readme-template.md`를 **규범(정본)** 으로 한다.
- README를 생성/갱신할 때는 반드시 해당 템플릿의 구조/섹션/필드를 유지한다.
- 템플릿을 변경하려면 사용자가 `readme-template.md`를 수정하며,
  포맷 변경은 본 문서(본 섹션)와의 정합성이 유지되어야 한다.
