# steps-rule.md

## Step Execution Documentation Rules

---

## 1. 이 문서의 목적

이 문서는 `/docs/steps/` 디렉토리에 위치하는 **Step 실행 문서**에 대한
작성 규칙과 실행 시 반드시 지켜야 할 제약을 정의한다.

- Step 문서는 **작업 단위(Task Unit)** 를 정의한다.
- Step 문서는 AI가 코드를 작성하고 테스트를 구현할 때 사용하는 **직접 실행 기준**이다.
- 본 문서는 상위 규칙 문서(`00-overview.md`, `01-rules.md` 등)를 위반하지 않으며,
  Step 레벨에서 필요한 **세부 실행 규칙을 보완**한다.

---

## 2. Step 문서의 역할 정의

Step 문서는 다음을 명확히 정의해야 한다.

- 이번 작업에서 **무엇을 할 것인지**
- 이번 작업에서 **무엇을 하지 않을 것인지**
- 어떤 문서/기준을 **참조해야 하는지**
- 어떤 조건을 만족해야 **완료로 간주되는지**

Step 문서는 “요구사항 전체 설명서”가 아니라,
**지금 단계에서 AI가 무엇을 실행해야 하는가**만을 정의한다.

---

## 3. Acceptance Criteria (AC)의 정의와 역할

### 3.1 AC란 무엇인가

Acceptance Criteria(수용 기준)는 **Step이 완료되었을 때 시스템이 만족해야 하는 구체적이고 검증 가능한 조건**이다.

- AC는 Step 문서에서 정의된다.
- 각 AC는 Given-When-Then 형식으로 기술된다.
- AC는 테스트 코드로 표현되어야 한다.

### 3.2 AC의 역할

- **테스트의 기준**: 각 AC는 하나 이상의 테스트 케이스와 매핑된다.
- **완료 판정의 기준**: 모든 AC가 충족되면 Step이 완료된 것으로 간주한다.
- **요구사항의 명시**: 추상적인 요구사항을 구체적인 검증 조건으로 변환한다.

### 3.3 AC 작성 규칙

- 단정형으로 작성한다. ("~할 수 있다", "~가 표시된다" 등)
- 추상적이거나 모호한 표현을 금지한다. ("예뻐야 한다", "적절히" 등)
- 사용자 관점과 시스템 관점이 모두 관찰 가능해야 한다.
- 각 AC는 독립적으로 테스트 가능해야 한다.

### 3.4 AC와 Scenario의 관계

- **Scenario**: 사용자 관점의 흐름 ("사용자가 무엇을 어떻게 경험하는가")
- **AC**: 개발자 관점의 검증 기준 ("시스템이 무엇을 어떻게 처리하는가")
- 하나의 Scenario는 여러 AC로 분해될 수 있다.

## 4. 디렉토리 구조 규칙

```
/docs/steps
 ├─ steps-rule.md        ← Step 문서 규칙 (본 문서)
 ├─ template.md          ← Step 문서 템플릿 (고정 포맷)
 ├─ step-01-*.md
 ├─ step-02-*.md
 └─ ...
```

- Step 문서는 `/docs/steps/` 하위에만 위치한다.
- Step 번호는 실행 순서를 의미하며, 로드맵과 1:1로 대응한다.
- Step 문서 파일명은 반드시 `step-XX-`(2자리 0-padding)로 시작한다.

---

## 5. Step 문서 독립성 원칙 (중요)

### 4.1 단일 Step 참조 원칙

- AI는 한 번의 작업 요청에서 **오직 하나의 Step 문서만 참조**한다.
- 다른 Step 문서는 존재하더라도 참조하지 않는다.
- 이전 Step의 내용은 자동으로 이어지지 않는다.

목적

- 컨텍스트(Token) 사용 최소화
- Step 간 결합도 제거
- 독립적 재실행 가능성 확보

---

### 4.2 명시적 참조 원칙

- Step 문서에서 참조하지 않은 문서는 존재하지 않는 것으로 간주한다.
- Step 문서가 참조할 수 있는 문서 범위는 다음으로 제한한다.
  - 규칙 문서(Rule Documents)
  - 도메인 문서(Domain Documents): `/docs/domains/`
  - 프로세스 문서(Process Documents)
  - Step 문서가 지정한 특정 시나리오 문서/구간
  - Step 문서가 지정한 특정 이슈 로그 파일(`/docs/issues/logs/...`)

AI는 암묵적 맥락(이전 대화, 다른 Step, 일반 상식)을 근거로 구현을 확장하지 않는다.

---

### 5.3 Default References (기본 참조 문서)

모든 Step 문서는 다음 문서를 항상 참조할 수 있다.
(Step 문서의 References 섹션에 명시적으로 기재할 필요 없음)

- `00-overview.md` (최상위 규칙)
- `01-rules.md` (도메인 및 개발 공통 규칙)
- `docs/steps/steps-rule.md` (Step 실행 규칙)

Step의 References 섹션에는 **Always Available (Default References)** 라는 헤더 아래에 위 3개 문서를 명시하고,
그 아래 **Step-Specific References** 라는 헤더로 Step이 특별히 참조하는 문서만 기재한다.

예시:
```markdown
## 3. References (Explicit Only)

### Always Available (Default References)
- 00-overview.md
- 01-rules.md
- docs/steps/steps-rule.md

### Step-Specific References
- docs/scenarios/scenario-01-create-todo.md (SCN-001)
- docs/domains/todo.md
```

## 6. 범위 및 추론 금지 규칙

### 5.1 범위 고정 원칙

- Step 문서의 범위(Scope)는 절대적 기준이다.
- `In Scope`에 없는 기능은 구현하지 않는다.
- `Out of Scope`에 포함된 항목은 의도적으로 구현하지 않는다.

### 5.2 요구사항 추론 금지

- Step 문서에 명시되지 않은 요구사항을 추론하지 않는다.
- "일반적으로 필요한 기능"을 이유로 기능/테스트를 추가하지 않는다.
- 모호하거나 충돌하는 부분은 이슈 로그로 기록한다.

---

## 7. Step 세부 실행 프로세스

개발 요청에서 "Step 프로세스 실행" 단계(01-rules.md 13.1의 4단계)에 해당하는
Step 내부의 세부 프로세스를 정의한다.

### 6.1 Step 레벨 프로세스 (N개 Step 반복)

요청된 모든 Step에 대해 다음 프로세스를 반복한다. 각 Step에서 문제가 발생해도 **작업을 즉시 중단하지 않고 이슈를 기록한 후 다음 Step으로 진행**한다.

**프로세스:**

1. **Step 선택**: 미완료 Step 선택
2. **문서 정독**: Step 문서와 Step에서 참조하는 문서만 정독
3. **TDD 사이클 실행**: Step 문서의 모든 AC가 충족될 때까지 다음 과정을 반복한다. (상세: Section 6.2 참조)
   - 테스트 코드 작성 (AC 기반)
   - 코드 구현 (최소 구현)
   - 테스트 검증 (모든 테스트 통과 확인)
   - 리팩토링 (필요시)
4. **TypeScript 타입 검사**: Step의 모든 AC가 충족된 후 수행 (상세: Section 6.3 참조)
5. **Step 단위 커밋**: 완료된 Step을 1개의 통합 커밋으로 기록 (상세: Section 6.4 참조)
6. **다음 Step으로 진행** (또는 모든 Step 완료 시 종료)

### 6.2 TDD 사이클의 상세 (AC 단위 반복)

Step 내에서 **Step 문서의 모든 AC가 충족될 때까지** 아래 Test-Driven Development(TDD) 사이클을 반드시 유지한다.

1. **테스트 코드 작성**: 현재 AC를 기반으로 Playwright E2E 테스트 케이스를 작성한다.
2. **코드 구현**: 작성된 테스트를 통과시키는 최소 구현을 작성한다.
3. **테스트 검증**: 작성한 코드가 모든 테스트를 통과하는지 확인한다.
4. **리팩토링**: 불안정하거나 복잡한 테스트/코드에 대해 리팩토링을 진행한다.
5. **다음 AC로 진행**: 현재 AC가 충족되면 다음 미충족 AC로 진행 (위 1)~4) 반복)

### 6.3 개발 환경 구성

**터미널 구성:**
```bash
# 터미널 1: 개발 서버 실행
npm run dev

# 터미널 2: 테스트 실행
npm run test:e2e
```

**작업 완료 전 검증:**
```bash
# TypeScript 타입 체크
npx tsc --noEmit
```

### 6.4 TypeScript 타입 검사

Step의 모든 AC가 충족되고 테스트가 통과한 후, 타입 검사를 반드시 수행한다.

```bash
npx tsc --noEmit
```

- 타입 검사가 통과하지 않으면 Step은 완료된 것으로 간주하지 않는다.
- 타입 에러를 수정한 후 테스트가 여전히 통과하는지 확인한다.

### 6.5 Step 단위 커밋

Step의 모든 작업이 완료되면(TDD 사이클 + 타입 검사), Step 단위 커밋을 생성한다.

**커밋 타이밍:**

- Step에 포함된 모든 테스트 케이스가 작성되었고,
- 모든 테스트가 통과하며,
- 필요한 리팩토링이 반영되었으며,
- TypeScript 타입 검사가 통과한 시점에 커밋을 생성한다.

**커밋 메시지 규칙:**

- 커밋 메시지는 **루트 디렉토리의 `.gitmessage` 컨벤션을 반드시 따른다.**
- `.gitmessage`가 존재하지 않거나 Step 문서가 이를 명시하지 않은 경우,
  커밋 컨벤션을 임의로 추론하지 않는다.
  - 이 경우 이슈 로그로 기록하고 사용자 판단을 요청한다.

**의의:**

- 이 커밋은 PR에서 Step 단위로 작업 내용을 추적/리뷰하기 위한 최소 단위다.

### 6.6 Step 실행 규칙

- 구현 코드를 테스트보다 먼저 작성하지 않는다.
- Step 문서에 없는 기능/테스트를 임의로 추가하지 않는다.
- 각 Step은 **독립적으로 개발 가능**해야 한다.
  - 특정 데이터나 기능이 필요하면 테스트 내에서 구성 (mock 데이터, fixture 등)
  - 다른 Step의 완료 상태에 의존하지 않는다.

### 7.7 테스트 도구 규칙 (Playwright)

**기본값 (Default)**

- 본 프로젝트의 사용자 관점 테스트(E2E)는 **Playwright**를 기본 도구로 사용한다.
- Step 문서에서 별도 지시가 없는 한, 모든 사용자 시나리오 검증은 Playwright 테스트로 작성한다.

**테스트 파일 관리**

- 테스트 파일명/경로/네이밍은 Step 문서의 "Test Specification" 섹션에서 명시한다.
- 명시되지 않은 경우 새로운 테스트 명명 규칙을 임의로 도입하지 않는다.

**단위 테스트(Unit) 도구**

- 단위 테스트(Vitest, Jest 등)의 도입은 기본값이 아니다.
- 필요 시 Step 문서에서만 명시적으로 허용한다.

## 8. 실행 중 문제 발생 시 규칙

- 판단이 불가능한 문제가 발생하면:
  - 작업을 즉시 중단하지 않는다.
  - 문제의 영향 범위를 식별한다.
  - 문제가 되는 기능을 **제외/비활성화/스텁 처리**하여 작업을 계속한다.
  - 동시에 `/docs/issues/logs/`에 **실행 단위 이슈 로그**를 기록한다.

- 다음 상황에서는 작업을 중단하고 사용자 판단을 요청한다.
  - 규칙 문서 간 충돌로 올바른 동작을 결정할 수 없는 경우
  - 데이터 손실 또는 보안 위험 가능성이 있는 경우
  - 빌드 또는 테스트가 불가능한 상태가 되는 경우

---

## 9. Step 문서 템플릿 준수 규칙 (필수)

- 모든 Step 문서는 `/docs/steps/template.md`(또는 Step 템플릿으로 지정된 파일)의 규칙과 구조를 따른다.
- Step 문서가 템플릿을 위반하면 유효한 실행 기준으로 간주하지 않는다.

우선순위

- 상위 규칙 문서 → steps-rule → step-template → 개별 Step 문서

---

## 10. Step 완료 기준 (Definition of Done)

Step은 다음 조건을 모두 만족해야 완료로 간주된다.

- Step 문서에 명시된 Acceptance Criteria가 모두 충족됨
- 관련 테스트 코드가 존재하고 통과함
- Step 문서에 정의된 산출물이 모두 생성됨
- **Step 단위 커밋이 존재함**
- 작업 결과에 대해 Pull Request(PR)가 생성됨

PR 생성 이후

- 리뷰 및 머지는 사용자의 책임이다.
- AI는 리뷰 결과를 추론하거나 반영하지 않는다.

---

## 11. Step 문서 수정 규칙

- Step 문서는 사용자만 수정할 수 있다.
- AI는 Step 문서를 직접 수정하지 않는다.
- Step 문서 수정 이후 동일 Step을 재요청하는 경우:
  - 기존 결과물을 기준선(Baseline)으로 삼고
  - 변경된 부분의 영향 범위만 수정한다.
- 전체 재구현이 필요하면, 그 사유를 사용자에게 명시적으로 보고한다.

## 12. Design Reference 부재 시 추론 금지 규칙

- Step 문서의 References 섹션에 Design 항목이 명시되지 않은 경우,
  해당 Step에는 UI/디자인에 대한 외부 결정이 존재하지 않는 것으로 간주한다.
- 이 경우 AI는 다음을 절대 수행하지 않는다.
  - Figma, 디자인 시안, 디자인 시스템의 존재를 가정하거나 추론하는 행위
  - 일반적인 UI 패턴, 관례, 이전 Step 또는 과거 대화를 근거로 한 디자인 결정
  - 시각적 완성도, 미적 요소를 고려한 구현 확장
- Design Reference가 없는 Step에서 AI는:
  - Acceptance Criteria를 충족하기 위한 최소한의 UI만 구현한다.
  - 기능 검증과 테스트 통과를 목적으로 한 비최적·비정교한 표현을 허용한다.
  - UI의 구조, 배치, 스타일은 추후 Step에서 변경 가능함을 전제로 구현한다.
- Design Reference의 부재는 자유 구현의 허용이 아니라,
  디자인 결정에 대한 추론 금지 및 제약 제거 상태를 의미한다.

---

## 13. Step 실행 중 타임아웃 정책

Step 실행 중 문제로 인한 20분 이상의 지체 발생 시, AI는 다음 규칙을 따른다.

### 13.1 20분 지체 시 즉시 중단 원칙

어떤 문제든 20분 이상 지체되면 AI는 즉시 개발을 중단하고 이슈를 기록해야 한다.

**목적:**

- 사용자의 시간 낭비 방지
- 명확한 차단 상황 인식
- 효율적인 작업 관리

### 13.2 중단 시 수행 절차

다음 순서를 따른다:

1. **즉시 중단**: 현재 작업 중단
2. **이슈 작성**: `/docs/issues/logs/ISS-YYYY-MM-DD-HHMM-timeout.md` 형식으로 파일 생성
3. **상세 기록** (이슈 파일에 포함):
   - 문제 상황 (무엇이 안 되었는가)
   - 시도한 해결책 (어떤 시도를 했는가)
   - 현재 상태 (어디까지 진행되었는가)
   - 차단 요인 (무엇이 진행을 막는가)
4. **의사결정 요청**: 다음 중 하나 선택 후 사용자 판단 대기
   - 다음 Step 진행 가능 여부
   - 현재 Step 재시도 전략
   - 개발 중단

### 13.3 다음 Step 진행 가능 조건

현재 Step에서 20분 이상 지체되었을 때:

**다음 Step을 진행할 수 있는 경우**

- 현재 Step의 AC가 이미 충족되어 있는 경우
- 현재 Step의 문제가 다음 Step에 영향을 주지 않는 경우

**다음 Step을 진행할 수 없는 경우**

- 현재 Step의 기능이 다음 Step의 전제조건인 경우
- 현재 Step 없이는 프로젝트가 실행 불가능한 경우
- 기본 개발 환경 구성 관련 문제인 경우

### 13.4 AI의 책임

- 20분 지체 상황을 정확히 판단하고 즉시 기록한다.
- 이슈 파일의 내용이 명확하고 재현 가능하도록 작성한다.
- 사용자의 판단을 기다리며, 판단 없이 독단적으로 진행하지 않는다.

### 13.5 예외 없음

- 거의 해결될 것 같아도 20분을 초과하면 즉시 중단
- "곧 될 것 같은데" 같은 예측에 의존하지 않음
- 엄격한 타임라인 준수
