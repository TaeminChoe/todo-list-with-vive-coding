# 01-rules.md

## Domain & Development Rules

---

## 1. 이 문서의 역할

이 문서는 **애플리케이션 도메인과 개발 전반에 적용되는 공통 규칙을 정의한다.**

- 기능 구현 시 반드시 지켜야 할 제약 조건을 명시한다.
- Step 문서에서 세부 규칙을 정의할 때, **이 문서를 기반으로 확장한다.**
- 코드, 테스트, Step 문서보다 **항상 우선하는 기준 문서**다.

---

## 2. 규칙의 적용 범위

이 문서의 규칙은 다음 대상에 **동일하게 적용된다.**

- 애플리케이션 코드
- 테스트 코드
- Step 실행 문서에서 정의되는 모든 기능
- AI가 수행하는 모든 개발 작업

---

## 3. 규칙 정의 원칙

### 3.1 단정형 규칙 원칙

모든 규칙은 **단정형 문장**으로 정의한다.

- ❌ “~일 수 있다”
- ❌ “상황에 따라”
- ❌ “필요하면”

- ✅ “~한다”
- ✅ “~이어야 한다”
- ✅ “~하지 않는다”

단정형으로 정의되지 않은 규칙은  
**존재하지 않는 규칙으로 간주**한다.

---

### 3.2 암묵적 규칙 금지

문서에 명시되지 않은 규칙은 **존재하지 않는다.**

- 관례
- 추론
- 일반적인 UX 패턴
- 유사 서비스의 동작

위 항목들은 **규칙의 근거가 될 수 없다.**

---

## 4. 데이터 및 상태에 대한 일반 규칙

### 4.1 데이터의 명시적 정의

- 모든 데이터 구조는 명확한 필드와 타입을 가진다.
- 자유 형식 데이터 구조는 허용하지 않는다.
- 필드가 정의되지 않았다면, 해당 데이터는 존재하지 않는다.

---

### 4.2 상태(State)의 제한

- 상태는 **유한한 집합**으로 정의한다.
- 문자열 자유 입력을 상태로 사용하지 않는다.
- 상태 전이는 명시적으로 정의된 경우에만 허용된다.

---

## 5. 사용자 행동 규칙

### 5.1 사용자 행동은 시나리오로만 정의된다

- 사용자가 수행할 수 있는 모든 행동은 시나리오 문서에 정의되어야 한다.
- 시나리오에 없는 행동은 **허용되지 않은 행동**으로 간주한다.

---

### 5.2 예외 상황도 정상 시나리오다

- 에러
- 실패
- 빈 상태
- 잘못된 입력

위 항목들은 모두 **정상적인 사용자 시나리오의 일부**로 정의한다.

---

## 6. 구현 관련 공통 규칙

### 6.1 최소 구현 원칙

- 테스트를 통과하는 **최소한의 구현**만 허용한다.
- 미래를 가정한 확장 구현은 금지한다.

---

### 6.2 중복 금지

- 동일한 로직은 한 번만 구현한다.
- 중복 발견 시 즉시 리팩토링 대상이 된다.

---

### 6.3 명시적 실패 처리

- 실패는 숨기지 않는다.
- 에러는 명시적으로 처리되거나 노출되어야 한다.
- 무시되는 에러는 허용하지 않는다.

---

## 7. 테스트 관련 규칙

### 7.1 테스트는 규칙의 실행 표현이다

- 테스트는 기능 검증 도구가 아니라 **규칙을 실행한 결과물**이다.

---

### 7.2 테스트 없는 기능은 존재하지 않는다

- 테스트가 없다면 해당 기능은 구현되지 않은 것으로 간주한다.
- 테스트가 실패하는 기능은 완료되지 않은 기능이다.

## 테스트 프레임워크 고정 규칙 (Playwright)

- 본 프로젝트의 사용자 관점 테스트(E2E)는 **Playwright**를 기본 도구로 사용한다.
- Step 문서에서 별도 지시가 없는 한, 모든 사용자 시나리오 검증은 Playwright 테스트로 작성한다.
- 테스트 파일/경로/네이밍은 Step 문서에서 명시한다. (명시되지 않은 경우 새 규칙을 임의로 도입하지 않는다.)
- 단위 테스트(Unit) 도구의 도입(예: Vitest/Jest)은 기본값이 아니며, 필요 시 Step 문서에서만 명시적으로 허용한다.

---

## 8. AI 작업에 대한 규칙

### 8.1 추론 제한

- AI는 문서에 없는 요구사항을 추론하지 않는다.
- 일반적인 관례를 근거로 구현하지 않는다.

---

### 8.2 문서 우선 원칙

- 문서와 코드가 충돌하면 **문서가 항상 우선**한다.
- 문서 간 충돌 발견 시 구현을 중단하고 이슈로 기록한다.

---

## 9. 규칙 변경 원칙

- 규칙 변경은 반드시 문서 수정으로 시작한다.
- 코드 수정으로 규칙을 우회하지 않는다.
- 규칙 변경 시 영향을 받는 Step 문서를 검토한다.

---

## 10. 폴더 구조에 대한 공통 규칙

### 10.1 문서 디렉토리 규칙

- `/docs` 디렉토리는 항상 프로젝트 루트에 존재해야 한다.
- `/docs`는 문서 전용 디렉토리다.
- `/docs` 내부에는 실행 코드, 설정 코드, 테스트 코드를 두지 않는다.

---

### 10.2 코드와 문서 분리 규칙

- 애플리케이션 실행 코드는 문서 디렉토리와 물리적으로 분리되어야 한다.
- 문서와 코드가 동일한 디렉토리에 공존하는 구조는 허용하지 않는다.

---

### 10.3 테스트 코드 위치 규칙

- 테스트 코드는 프로덕션 코드와 명확히 분리된 위치에 존재해야 한다.
- 테스트 코드 위치는 프로젝트 내에서 일관되게 유지되어야 한다.
- 테스트 코드가 산재하는 구조는 허용하지 않는다.

---

### 10.4 산출물 생성 규칙

- 빌드 산출물은 소스 코드와 동일한 디렉토리에 생성하지 않는다.
- 자동 생성 파일은 명시적으로 구분 가능한 위치에 생성한다.

---

## 12. npm 명령어 실행 규칙 (개발 환경 도구)

### 12.1 npm 실행 방식

npm 명령어는 교차 플랫폼 호환성을 보장하기 위해 npm.cmd를 우선적으로 호출한다.  
 환경에 따라 다음 순서로 시도한다:

**npm 명령어 실행 패턴 (우선순위):**

```bash
# 1순위: npm.cmd 직접 호출 (Windows, macOS, Linux 모두 호환)
npm.cmd install
npm.cmd run dev
npm.cmd run build
npm.cmd run test:e2e

# 대체 방식 (npm.cmd 실패 시)
npm install
npm run dev
npm run build
npm run test:e2e

# 최후 방식 (npm이 PATH에 없을 때)
npx npm install
npx npm run dev
npx npm run build
npx npm run test:e2e

12.2 적용 범위

- 모든 Step 실행 시 npm 명령어가 필요하면 위 패턴을 따른다.
- AI는 npm.cmd를 기본으로 사용하고, 실패 시 대체 방식을 시도한다.
- CI/CD 환경에서도 동일하게 적용된다.
- npm.cmd는 npm 래퍼로서 모든 플랫폼에서 동일하게 작동한다.
```

## 13. 개발 실행 프로세스

### 13.1 개발 요청 사이클 프로세스

사용자가 개발을 요청했을 때 AI가 한 사이클 동안 수행하는 절차다.

**단계 순서:**

1. **브랜치 생성**: Feature branch를 생성하여 작업을 시작한다.
   - 브랜치명 규칙: `feature/cycle-XXX-{summary}`
   - XXX: 3자리의 증가하는 번호 (001, 002, 003, ...)
   - summary: 사용자가 지정하거나, 개발 내용을 2~3개 단어로 간단히 표현 (단어는 `-`로 이어짐)
   - 예시: `feature/cycle-001-edit-flow-chart`

2. **문서 검증**: 요청 범위에 포함된 사용자 작성 문서의 규칙/템플릿 준수 여부를 검증한다.
   - 검증 대상: Step 문서(step-XX-*.md), Scenario 문서(scenario-XX-*.md) 등 사용자가 작성한 문서
   - 검증 항목:
     1) 각 문서들의 정의/개념 중 충돌이 발생하는지 확인
     2) 각 문서가 해당 문서의 역할 규칙(steps-rule.md, scenarios-rule.md 등)을 준수하는지 확인
     3) 각 문서가 템플릿(template.md)을 따라 작성되었는지 확인
   - 규칙 위반 또는 충돌 발견 시 이슈로 기록한다.
   - Context 최적화를 위해 형식/구조 규칙 준수 여부만 확인하고, 내용 이해/정리는 수행하지 않는다.

3. **모든 Step 개발 진행**: 요청된 모든 Step에 대해 Step 프로세스를 실행한다.
   - 각 Step마다:
     - 시나리오/AC 확인
     - TDD 사이클 (테스트 작성 → 구현 → 검증 → 리팩토링)
     - TypeScript 타입 검사
     - Step 단위 커밋 (`.gitmessage` 컨벤션 준수)
   - 상세 프로세스는 `steps-rule.md`의 Section 6과 `step-cycle.mmd`를 참조한다.

4. **Pull Request(PR) 작성**: 모든 Step 완료 후 Feature branch를 PR로 변환하여 리뷰를 요청한다.

**책임 범위:**

- AI는 위 1~4단계를 모두 수행한다.
- PR 리뷰 이후의 머지(Merge)는 사용자의 책임이다.
- AI는 머지 판단을 대신하지 않는다.

## 14. Git 커밋 컨벤션 규칙

### 14.1 .gitmessage 규칙 준수 (필수)

- 모든 Git 커밋은 **루트 디렉토리의 `.gitmessage` 파일에 정의된 컨벤션을 반드시 따른다.**
- `.gitmessage`는 프로젝트의 커밋 메시지 형식 기준(Source of Truth)이다.
- 커밋 메시지는 단정형 문장으로 작성하며, 규칙에 명시되지 않은 형식은 사용하지 않는다.

### 14.2 커밋 메시지 적용 시점

- **Step 단위 커밋**: Step 실행이 완료되면 1개의 통합 커밋을 생성 (`.gitmessage` 규칙 준수)
- **기타 커밋**: 문서 수정, 설정 변경 등 필요에 따라 생성 (동일하게 `.gitmessage` 규칙 준수)
- 규칙 미준수 커밋은 완료되지 않은 커밋으로 간주한다.
