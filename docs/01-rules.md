# 01-rules.md

## Domain & Development Rules

---

## 1. 이 문서의 역할

이 문서는 **애플리케이션 도메인과 개발 전반에 적용되는 공통 규칙을 정의한다.**

- 기능 구현 시 반드시 지켜야 할 제약 조건을 명시한다.
- Step 문서에서 세부 규칙을 정의할 때, **이 문서를 기반으로 확장한다.**
- 코드, 테스트, Step 문서보다 **항상 우선하는 기준 문서**다.

---

## 2. 규칙의 적용 범위

이 문서의 규칙은 다음 대상에 **동일하게 적용된다.**

- 애플리케이션 코드
- 테스트 코드
- Step 실행 문서에서 정의되는 모든 기능
- AI가 수행하는 모든 개발 작업

---

## 3. 규칙 정의 원칙

### 3.1 단정형 규칙 원칙

모든 규칙은 **단정형 문장**으로 정의한다.

- ❌ “~일 수 있다”
- ❌ “상황에 따라”
- ❌ “필요하면”

- ✅ “~한다”
- ✅ “~이어야 한다”
- ✅ “~하지 않는다”

단정형으로 정의되지 않은 규칙은  
**존재하지 않는 규칙으로 간주**한다.

---

### 3.2 암묵적 규칙 금지

문서에 명시되지 않은 규칙은 **존재하지 않는다.**

- 관례
- 추론
- 일반적인 UX 패턴
- 유사 서비스의 동작

위 항목들은 **규칙의 근거가 될 수 없다.**

---

## 4. 데이터 및 상태에 대한 일반 규칙

### 4.1 데이터의 명시적 정의

- 모든 데이터 구조는 명확한 필드와 타입을 가진다.
- 자유 형식 데이터 구조는 허용하지 않는다.
- 필드가 정의되지 않았다면, 해당 데이터는 존재하지 않는다.

---

### 4.2 상태(State)의 제한

- 상태는 **유한한 집합**으로 정의한다.
- 문자열 자유 입력을 상태로 사용하지 않는다.
- 상태 전이는 명시적으로 정의된 경우에만 허용된다.

---

## 5. 사용자 행동 규칙

### 5.1 사용자 행동은 시나리오로만 정의된다

- 사용자가 수행할 수 있는 모든 행동은 시나리오 문서에 정의되어야 한다.
- 시나리오에 없는 행동은 **허용되지 않은 행동**으로 간주한다.

---

### 5.2 예외 상황도 정상 시나리오다

- 에러
- 실패
- 빈 상태
- 잘못된 입력

위 항목들은 모두 **정상적인 사용자 시나리오의 일부**로 정의한다.

---

## 6. 구현 관련 공통 규칙

### 6.1 최소 구현 원칙

- 테스트를 통과하는 **최소한의 구현**만 허용한다.
- 미래를 가정한 확장 구현은 금지한다.

---

### 6.2 중복 금지

- 동일한 로직은 한 번만 구현한다.
- 중복 발견 시 즉시 리팩토링 대상이 된다.

---

### 6.3 명시적 실패 처리

- 실패는 숨기지 않는다.
- 에러는 명시적으로 처리되거나 노출되어야 한다.
- 무시되는 에러는 허용하지 않는다.

---

## 7. 테스트 관련 규칙

### 7.1 테스트는 규칙의 실행 표현이다

- 테스트는 기능 검증 도구가 아니라 **규칙을 실행한 결과물**이다.
- Acceptance Criteria는 반드시 테스트로 표현되어야 한다.

---

### 7.2 테스트 없는 기능은 존재하지 않는다

- 테스트가 없다면 해당 기능은 구현되지 않은 것으로 간주한다.
- 테스트가 실패하는 기능은 완료되지 않은 기능이다.

## 테스트 프레임워크 고정 규칙 (Playwright)

- 본 프로젝트의 사용자 관점 테스트(E2E)는 **Playwright**를 기본 도구로 사용한다.
- Step 문서에서 별도 지시가 없는 한, 모든 사용자 시나리오 검증은 Playwright 테스트로 작성한다.
- 테스트는 **시나리오/Acceptance Criteria(AC)** 를 근거로 작성하며, 문서에 없는 동작을 테스트로 추론하지 않는다.
- 테스트 파일/경로/네이밍은 Step 문서에서 명시한다. (명시되지 않은 경우 새 규칙을 임의로 도입하지 않는다.)
- 단위 테스트(Unit) 도구의 도입(예: Vitest/Jest)은 기본값이 아니며, 필요 시 Step 문서 또는 별도 의사결정(Decision)으로만 허용한다.

---

## 8. AI 작업에 대한 규칙

### 8.1 추론 제한

- AI는 문서에 없는 요구사항을 추론하지 않는다.
- 일반적인 관례를 근거로 구현하지 않는다.

---

### 8.2 문서 우선 원칙

- 문서와 코드가 충돌하면 **문서가 항상 우선**한다.
- 문서 간 충돌 발견 시 구현을 중단하고 이슈로 기록한다.

---

## 9. 규칙 변경 원칙

- 규칙 변경은 반드시 문서 수정으로 시작한다.
- 코드 수정으로 규칙을 우회하지 않는다.
- 규칙 변경 시 영향을 받는 Step 문서를 검토한다.

---

## 10. 폴더 구조에 대한 공통 규칙

### 10.1 문서 디렉토리 규칙

- `/docs` 디렉토리는 항상 프로젝트 루트에 존재해야 한다.
- `/docs`는 문서 전용 디렉토리다.
- `/docs` 내부에는 실행 코드, 설정 코드, 테스트 코드를 두지 않는다.

---

### 10.2 코드와 문서 분리 규칙

- 애플리케이션 실행 코드는 문서 디렉토리와 물리적으로 분리되어야 한다.
- 문서와 코드가 동일한 디렉토리에 공존하는 구조는 허용하지 않는다.

---

### 10.3 테스트 코드 위치 규칙

- 테스트 코드는 프로덕션 코드와 명확히 분리된 위치에 존재해야 한다.
- 테스트 코드 위치는 프로젝트 내에서 일관되게 유지되어야 한다.
- 테스트 코드가 산재하는 구조는 허용하지 않는다.

---

### 10.4 산출물 생성 규칙

- 빌드 산출물은 소스 코드와 동일한 디렉토리에 생성하지 않는다.
- 자동 생성 파일은 명시적으로 구분 가능한 위치에 생성한다.

---

## 11. 이 문서의 위상

이 문서는 `00-overview.md` 다음으로 우선하는  
**프로젝트 전반의 공통 규칙 문서**다.

이 문서의 규칙을 따르지 않는 구현은  
완료되지 않은 구현으로 간주한다.
