# 00-overview.md

**Universal Documentation & AI Collaboration Convention**

## 1. 이 문서의 목적

이 문서는 특정 애플리케이션을 설명하는 문서가 아니다.

이 문서는 AI와 협업하여 애플리케이션을 개발할 때 반드시 지켜야 할
문서 구조, 권한 분리, 작업 방식, 참조 규칙을 정의하는 **최상위 규칙 문서**다.

앞으로 생성되는 모든 프로젝트는 이 문서의 규칙을 그대로 상속하는 것을 전제로 한다.

---

## 2. 프로젝트 구조에 대한 공통 전제

Git 저장소의 루트 디렉토리는 애플리케이션 프로젝트 루트다.
실제 코드, 설정, 테스트는 모두 루트 기준으로 생성된다.

`/docs` 디렉토리는 프로젝트의 유일한 기준(Source of Truth)이다.

```txt
/
 ├─ docs/        ← 기준 문서 및 개발 규칙
 ├─ src/         ← 애플리케이션 코드
 ├─ tests/       ← 테스트 코드 (형태는 프로젝트에 따라 다를 수 있음)
 └─ ...
```

## 3. 문서의 역할 분류 (Document Taxonomy)

모든 문서는 역할(Role)에 따라 분류된다.
문서 유형마다 권한, 책임, AI의 접근 방식이 다르다.

### 3.1 규칙 문서 (Rule Documents)

역할

- 프로젝트 전반에 적용되는 규칙을 정의한다.
- 개발 방식, 문서 구조, AI 협업 규칙을 명시한다.

예시

- `00-overview.md` (본 문서)
- `01-rules.md`
- `docs/scenarios/scenarios-rule.md`
- `docs/steps/steps-rule.md`
- `docs/issues/issue-rule.md`

규칙

- 선언형, 단정형 문장만 사용한다.
- 애매한 표현("상황에 따라", "가능할 수 있다")은 금지한다.
- 코드나 테스트보다 항상 우선한다.

수정 권한

- 사용자만 수정 가능
- AI는 읽기 및 검토만 가능

---

### 3.2 Step 실행 문서 (Step Execution Documents)

역할

- AI가 실제로 작업을 수행할 때 사용하는 **유일한 실행 기준 문서**다.
- 특정 단계에서 무엇을, 어디까지, 어떤 기준으로 수행할지 정의한다.

예시

- `/docs/steps/step-01-init.md`
- `/docs/steps/step-03-feature-x.md`

공통 구조(필수)

- 목적
- 범위(포함 / 제외)
- 선행 조건
- 사용자 시나리오
- 테스트 케이스
- 구현 제약 / 금지사항
- 완료 체크리스트(Definition of Done)

규칙

- Step 문서에 없는 기능은 구현하지 않는다.
- Step 문서에 명시되지 않은 요구사항을 추론하지 않는다.

수정 권한

- 사용자만 수정 가능
- AI는 절대 수정하지 않는다

---

### 3.3 도메인 문서 (Domain Documents)

역할

- 애플리케이션의 **데이터 모델과 상태**를 정의한다.
- Step과 Scenario에서 참조하는 **기준이 되는 데이터 정의**다.
- 사용자 경험(Scenario)과 기술적 구현(Step)의 중간 계층으로 작동한다.

예시

- `/docs/domains/todo.md`
- `/docs/domains/user.md`

규칙

- 데이터 구조, 필드, 제약조건을 명시적으로 정의한다.
- 상태는 유한한 집합으로 정의한다.
- 단정형 문장만 사용한다.

수정 권한

- 사용자만 수정 가능
- AI는 읽기 및 검토만 가능

---

### 3.4 이슈 문서 (Issue Documents)

역할

- 이슈 문서는 "문제 단위 기록"이 아니라 **실행 단위 기반의 문제 기록 로그**다.
- AI가 작업을 진행하는 과정에서 스스로 판단할 수 없는 문제를
  사용자에게 위임하고, 그 사실을 **실행 흐름 속에서 추적 가능하게 남기기 위한 문서**다.
- 문서를 직접 수정하지 않고도 문제를 관리하고,
  작업을 중단하지 않은 채 진행 상황을 기록하기 위한 수단이다.

중요한 개념 정리

- 하나의 이슈 파일은 "하나의 문제"를 의미하지 않는다.
- 하나의 이슈 파일은 **하나의 실행 시점(Execution Unit)** 을 의미한다.
- 하나의 실행 단위 이슈 파일 안에서:
  - 새로운 Issue ID가 등장할 수 있고
  - 기존 Issue ID의 상태(Open / Addressed / Resolved)가 갱신될 수 있다.

디렉토리 구조

```
/docs/issues
 ├─ README.md              ← 이슈 요약 및 현재 상태 인덱스
 ├─ issue-rule.md          ← 이슈 작성 및 생명주기 규칙
 ├─ template.md            ← 이슈 템플릿
 └─ logs/
     └─ ISS-YYYY-MM-DD-HHMM-[context].md  ← 실행 단위 이슈 로그
```

파일 구조 및 네이밍

- 실행 단위 이슈 로그 파일은 다음 형식으로 작성한다.

```
ISS-YYYY-MM-DD-HHMM-[context].md
```

규칙

- 이슈 로그 파일은 반드시 `/docs/issues/logs/` 하위에 생성한다.
- `/docs/issues/` 루트에는 규칙 문서, 템플릿, 요약 문서만 위치한다.
- 이슈 로그 파일은 **실행 단위 기준으로 생성**한다.
- 이슈 로그 파일은 수정하지 않으며, 새로운 실행이 발생할 때마다 새 파일을 생성한다.
- Issue ID는 문제 단위로 관리되며,
  하나의 Issue ID는 여러 실행 단위 이슈 로그 파일에 걸쳐 등장할 수 있다.
- Issue ID의 상세 생명주기 및 관리 방식은 `/docs/issues/issue-rule.md`를 따른다.

수정 권한

- 사용자
  - `issue-rule.md`, `template.md`, `README.md` 수정 가능
  - 이슈 로그 파일은 원칙적으로 수정하지 않고, 후속 로그 파일로 상태 변화를 기록
- AI
  - 규칙 문서, 템플릿, README 수정 불가
  - 작업 중 필요 시 **새 실행 단위 이슈 로그 파일(`/docs/issues/logs/ISS-...*.md`) 생성 가능**

### (추가) 이슈 요약 문서에 대한 관점

- `/docs/issues/README.md`는 실행 로그를 기반으로 한 **요약 리포트**다.
- README는 자동 생성될 수 있으며, 기준 문서가 아니다.
- 이슈에 대한 모든 사실과 판단의 근거는 `/docs/issues/logs/ISS-*.md`에만 존재한다.
- README는 사용자가 다음 판단(문서 수정 여부)을 빠르게 하기 위한 보조 수단이다.

## 4. AI의 문서 참조 규칙 (중요)

AI는 모든 문서를 한 번에 읽지 않는다.

AI가 참조할 수 있는 문서 범위

항상 참조 가능

- 규칙 문서(Rule Documents)

작업 단계 수행 시

- 해당 Step 실행 문서 1개
- (필요 시) Step 문서가 명시적으로 참조한 문서만 추가로 참조한다.
  - 예: 특정 도메인 문서, 특정 시나리오/AC 문서, 특정 프로세스 문서, 특정 이슈 파일

AI가 참조하지 않는 것

- 다른 Step 문서
- 향후 단계 문서
- 과거 단계의 세부 문서(명시되지 않은 경우)

목적

- 컨텍스트 낭비 방지
- 단계 간 결합도 최소화
- 작업 단위의 명확성 유지

---

## 5. AI의 권한과 제한

AI가 할 수 있는 것

- 규칙 문서와 Step 문서를 읽고 해석하기
- Step 문서 기준으로 테스트 코드 작성
- 테스트를 통과시키는 최소 구현 작성
- 코드 리팩토링
- 문서 간 논리적 오류를 이슈로 기록하기
- `/docs/issues/` 하위에 새 이슈 파일(ISS-...\*.md) 생성하기
- 작업이 완료되면 PR 생성 및 리뷰 요청하기

AI가 할 수 없는 것

- `/docs` 내 규칙 문서/로드맵/Step 실행 문서/프로세스 문서를 직접 수정하는 행위
- `/docs/issues/issue-rule.md`, `/docs/issues/template.md` 직접 수정
- 기존 이슈 파일(ISS-...\*.md) 내용 수정
- 문서에 없는 기능 추가
- 요구사항 추론 또는 확장
- 기준 문서를 변경하는 판단

---

## 6. 개발 진행의 절대 규칙

1. 문서는 기준이며, 코드는 결과물이다.
2. 테스트 없는 기능 구현은 허용하지 않는다.
3. 단계(Step) 단위로만 진행한다.
4. 완료 기준이 충족되지 않으면 다음 단계로 이동하지 않는다.
5. 모든 구조와 흐름은 다이어그램으로 검증 가능해야 한다.

---

## 7. AI의 증분 수정 규칙

문서가 수정된 이후 AI에게 동일한 Step 또는 작업을 다시 요청하는 경우, AI는 다음 원칙을 따른다.

### 7.1 기존 결과물 기준선 원칙

- AI는 기존에 생성된 코드, 테스트, 파일 구조를 기준선(Baseline)으로 삼는다.
- 문서 수정이 없는 영역의 코드는 변경하지 않는다.
- 전체 재작성은 허용되지 않는다.

### 7.2 변경 영향 범위 기반 수정

- AI는 수정된 문서의 변경 내용을 우선적으로 확인한다.
- 변경된 규칙, 시나리오, AC가 영향 미치는 범위만 식별하여 수정한다.
- 영향이 없는 Step, 기능, 테스트는 유지한다.

### 7.3 재구현 금지 원칙

- 문서 수정이 발생했다는 이유만으로 기존 구현을 폐기하거나 처음부터 다시 구현하지 않는다.
- 재구현이 필요한 경우, 그 사유를 명시적으로 사용자에게 보고해야 한다.

### 7.4 불확실성 보고 의무

- 변경 영향 범위를 명확히 판단할 수 없는 경우, AI는 임의로 수정하지 않고 사용자에게 판단을 요청한다.

---

## 8. AI 요청 수락 전 문서 검증 규칙

사용자가 문서를 수정한 후 AI에게 작업을 요청하는 경우, AI는 코드 작성 또는 테스트 작성을 시작하기 전에 반드시 문서 검증 단계를 수행한다.

### 8.1 사전 문서 검증 의무

- AI는 이번 요청에서 참조해야 할 문서를 식별한다.
- 각 문서에 대해, 해당 문서가 정의한 규칙을 준수했는지 검증한다.
- 검증 대상 문서는 다음을 포함한다.
  - 수정된 문서
  - 해당 문서가 참조하는 상위 규칙 문서

### 8.2 규칙 위반 및 불명확성 식별

- AI는 다음 항목을 반드시 식별하여 보고한다.
  - 문서 내부 규칙 위반
  - 상위 문서와의 충돌
  - 단정형이 아닌 표현
  - 시나리오/AC/Step 간 연결 불명확성
- 문제는 목록 형태로 명시적으로 제시한다.

### 8.3 수정 제안 및 판단 요청

- AI는 식별된 문제에 대해 수정 제안을 할 수 있다.
- AI는 스스로 문서를 수정하지 않는다.
- 문제 해결에 대한 최종 판단은 사용자에게 요청한다.

### 8.4 작업 시작 조건

- 다음 조건이 모두 충족되어야 작업을 시작할 수 있다.
  - 문서 검증 결과, 규칙 위반이 없다고 판단되었거나
  - 발견된 문제에 대해 사용자의 명시적 판단이 완료되었을 것
- 위 조건이 충족되지 않으면 AI는 코드를 작성하지 않는다.

### 8.5 무인 실행 안전성 보장

- 본 검증 단계는 사용자가 요청 후 즉시 모니터링하지 않는 상황을 전제로 한다.
- 문서 검증을 통과하지 않은 상태에서의 자동 코드 작성은 금지된다.

---

## 9. 이 문서의 위상

이 문서는 `/docs` 내 최상위 규칙 문서다.
이 문서의 내용은 다른 모든 문서와 코드보다 우선한다.

이 문서의 규칙을 따르지 않는 프로젝트는 본 협업 방식의 대상이 아니다.
