# 00-Overview.md

**Universal Documentation & AI Collaboration Convention**

## 1. 이 프로젝트의 목적

이 문서는 특정 애플리케이션을 설명하는 문서가 아니다.

이 문서는
AI와 협업하여 애플리케이션을 개발할 때 반드시 지켜야 할
문서 구조, 권한 분리, 작업 방식, 참조 규칙을 정의하는 최상위 규칙 문서다.

앞으로 생성되는 모든 프로젝트는
이 문서의 규칙을 그대로 상속하는 것을 전제로 한다.

---

## 2. 프로젝트 구조에 대한 공통 전제

Git 저장소의 루트 디렉토리는 애플리케이션 프로젝트 루트다.

실제 코드, 설정, 테스트는 모두 루트 기준으로 생성된다.

/docs 디렉토리는 프로젝트의 유일한 기준(Source of Truth) 이다.

```cmd
/
 ├─ docs/        ← 기준 문서 및 개발 규칙
 ├─ src/         ← 애플리케이션 코드
 ├─ tests/       ← 테스트 코드 (형태는 프로젝트에 따라 다를 수 있음)
 └─ ...
```

## 3. 문서의 역할 분류 (Document Taxonomy)

모든 문서는 역할(Role) 에 따라 분류된다.

문서 유형마다 권한, 책임, AI의 접근 방식이 다르다.

### 3.1 규칙 문서 (Rule Documents)

역할

- 프로젝트 전반에 적용되는 규칙을 정의한다.
- 개발 방식, 문서 구조, AI 협업 규칙을 명시한다.

예시

- `00-overview.md` (본 문서)
- `01-rules.md` (도메인 규칙)
- `02-scenarios.md`
- `03-acceptance-criteria.md`

규칙

- 선언형, 단정형 문장만 사용한다.
- 애매한 표현(“상황에 따라”, “가능할 수 있다”)은 금지한다.
- 코드나 테스트보다 항상 우선한다.

수정 권한

- 사용자만 수정 가능
- AI는 읽기 및 검토만 가능

### 3.2 로드맵 문서 (Roadmap Documents)

역할

- 프로젝트의 전체 진행 순서와 단계를 정의한다.
- 각 단계(Step)의 목적과 산출물을 명시한다.

예시

- `04-roadmap.md`

규칙

- 단계 번호는 실행 순서와 1:1로 대응한다.
- 로드맵은 “현재 위치 확인”을 위한 문서다.

수정 권한

- 사용자만 수정 가능
- AI는 참조만 가능

### 3.3 Step 실행 문서 (Step Execution Documents)

역할

- AI가 실제로 작업을 수행할 때 사용하는 유일한 실행 기준 문서
- 특정 단계에서 무엇을, 어디까지, 어떤 기준으로 수행할지 정의한다.

예시

- `/docs/steps/step-01-init.md`
- `/docs/steps/step-03-feature-x.md`

공통 구조 (필수)

- 목적
- 범위 (포함 / 제외)
- 선행 조건
- 사용자 시나리오
- Acceptance Criteria
- 테스트 케이스
- 구현 제약 / 금지사항
- 완료 체크리스트 (Definition of Done)

규칙

- Step 문서에 없는 기능은 구현하지 않는다.
- Step 문서에 명시되지 않은 요구사항을 추론하지 않는다.
- 해당 Step의 AC가 곧 테스트 기준이다.

수정 권한

- 사용자만 수정 가능
- AI는 절대 수정하지 않는다

### 3.4 의사결정 기록 문서 (Decision Documents)

역할

- 기술적/구조적 선택의 이유를 기록한다.
- 이후 리팩토링이나 확장 시 판단 기준으로 사용한다.

예시

- `/docs/decisions/0001-xxx.md`

규칙

- “무엇을 했는가”보다 “왜 선택했는가”를 기록한다.
- 간결함을 유지한다.

수정 권한

- 사용자만 수정 가능
- AI는 참조만 가능

### 3.5 이슈 / 검토 문서 (Issue Documents)

역할

- 문서 간 충돌, 누락, 모호한 정의를 기록한다.
- 문서를 직접 수정하지 않고 문제를 관리하기 위한 공간이다.

예시

- `/docs/issues.md`

규칙

- 문제만 기록한다.
- 해결책, 구현 아이디어, 판단은 기록하지 않는다.

수정 권한

- 사용자: 수정 가능
- AI: 문제 제안만 가능

### 3.6 다이어그램 문서 (Diagram Documents)

역할

- 전체 구조와 흐름을 시각적으로 검증한다.
- 구현 디테일이 아닌 논리적 관계를 표현한다.

예시

- `/docs/diagrams/*.mmd`

규칙

- Mermaid 문법 사용
- 개념, 단계, 상태 전이를 중심으로 표현한다.

수정 권한

- 사용자만 수정 가능
- AI는 검토 및 해석만 가능

### 3.7 실행 프로세스 문서 (Execution Process Documents)

역할

- 문서를 기준으로 한 실제 개발 실행 흐름을 정의한다.
- AI가 Step 문서를 전달받았을 때 어떤 순서로 작업을 수행하고, 어디까지 책임지는지를 명확히 규정한다.
- 본 문서는 “무엇을 만드는가”가 아니라 “어떻게 작업을 진행하는가”에 대한 규칙을 다룬다.

정의되는 범위

- Step 시작 조건
- AI의 작업 순서
  - 테스트 코드 작성 → 기능 구현 → 테스트 검증 → 리팩토링 → PR 작성
- 작업 완료의 기준
- 실패 또는 테스트 미통과 시 재작업 규칙

AI의 책임 범위

- Step 문서를 기준으로 작업 범위를 확정한다.
- 테스트 코드를 먼저 작성한다.
- 테스트를 통과하는 최소 구현을 작성한다.
- 테스트 통과 후 리팩토링을 수행한다.
- 작업이 완료되면 Pull Request(PR)를 생성하여 리뷰를 요청한다.

명시적 제한

- PR 리뷰 이후의 머지(Merge)는 AI의 책임 범위에 포함되지 않는다.
- 리뷰 반영 여부, 수정 요청 수용, 최종 머지는 사용자의 역할이다.
- AI는 머지 판단을 대신하지 않는다.

예시

- `/docs/process/01-development-workflow.md`
- `/docs/process/02-pr-workflow.md`

규칙

- 실행 프로세스 문서는 모든 Step 실행 시 항상 참조된다.
- Step 문서에는 실행 절차를 중복 정의하지 않는다.
- 실행 방식 변경은 프로세스 문서 수정으로만 이루어진다.

수정 권한

- 사용자만 수정 가능
- AI는 참조만 가능하며, 직접 수정할 수 없다

---

## 4. AI의 문서 참조 규칙 (중요)

AI는 모든 문서를 한 번에 읽지 않는다.

AI가 참조할 수 있는 문서 범위

항상 참조 가능:

- 규칙 문서 (Rule Documents)

작업 단계 수행 시:

- 해당 Step 실행 문서 1개
- 필요 시, 명시적으로 연결된 규칙 문서 일부

AI가 참조하지 않는 것

- 다른 Step 문서
- 향후 단계 문서
- 과거 단계의 세부 문서 (명시되지 않은 경우)

목적

- 컨텍스트 낭비 방지
- 단계 간 결합도 최소화
- 작업 단위의 명확성 유지

---

## 5. AI의 권한과 제한

AI가 할 수 있는 것

- 규칙 문서와 Step 문서를 읽고 해석하기
- Step 문서 기준으로 테스트 코드 작성
- 테스트를 통과시키는 최소 구현 작성
- 코드 리팩토링
- 문서 간 논리적 오류를 issues로 제안

AI가 할 수 없는 것

- /docs 내 문서를 직접 수정하는 행위
- 문서에 없는 기능 추가
- 요구사항 추론 또는 확장
- 기준 문서를 변경하는 판단

---

## 6. 개발 진행의 절대 규칙

1. 문서는 기준이며, 코드는 결과물이다.
2. 테스트 없는 기능 구현은 허용하지 않는다.
3. 단계(Step) 단위로만 진행한다.
4. 완료 기준이 충족되지 않으면 다음 단계로 이동하지 않는다.
5. 모든 구조와 흐름은 다이어그램으로 검증 가능해야 한다.

---

## 7. AI의 증분 수정 규칙

문서가 수정된 이후 AI에게 동일한 Step 또는 작업을 다시 요청하는 경우,
AI는 다음 원칙을 따른다.

### 7.1 기존 결과물 기준선 원칙

- AI는 기존에 생성된 코드, 테스트, 파일 구조를 **기준선(Baseline)** 으로 삼는다.
- 문서 수정이 없는 영역의 코드는 변경하지 않는다.
- 전체 재작성은 허용되지 않는다.

### 7.2 변경 영향 범위 기반 수정

- AI는 수정된 문서의 변경 내용을 우선적으로 확인한다.
- 변경된 규칙, 시나리오, AC가 **영향을 미치는 범위만** 식별하여 수정한다.
- 영향이 없는 Step, 기능, 테스트는 유지한다.

### 7.3 재구현 금지 원칙

- 문서 수정이 발생했다는 이유만으로
  기존 구현을 폐기하거나 처음부터 다시 구현하지 않는다.
- 재구현이 필요한 경우, 그 사유는 명시적으로 사용자에게 보고되어야 한다.

### 7.4 불확실성 보고 의무

- 변경 영향 범위를 명확히 판단할 수 없는 경우,
  AI는 임의로 수정하지 않고 사용자에게 판단을 요청한다.

---

## 8. AI 요청 수락 전 문서 검증 규칙

사용자가 문서를 수정한 후 AI에게 작업을 요청하는 경우,
AI는 코드 작성 또는 테스트 작성을 시작하기 전에
반드시 문서 검증 단계를 수행한다.

### 8.1 사전 문서 검증 의무

- AI는 이번 요청에서 참조해야 할 문서를 식별한다.
- 각 문서에 대해, 해당 문서가 정의한 규칙을 준수했는지 검증한다.
- 검증 대상 문서는 다음을 포함한다:
  - 수정된 문서
  - 해당 문서가 참조하는 상위 규칙 문서

### 8.2 규칙 위반 및 불명확성 식별

- AI는 다음 항목을 반드시 식별하여 보고한다.
  - 문서 내부 규칙 위반
  - 상위 문서와의 충돌
  - 단정형이 아닌 표현
  - 시나리오/AC/Step 간 연결 불명확성
- 문제는 목록 형태로 명시적으로 제시한다.

### 8.3 수정 제안 및 판단 요청

- AI는 식별된 문제에 대해 수정 제안을 할 수 있다.
- AI는 스스로 문서를 수정하지 않는다.
- 문제 해결에 대한 최종 판단은 사용자에게 요청한다.

### 8.4 작업 시작 조건

- 다음 조건이 모두 충족되어야 작업을 시작할 수 있다.
  - 문서 검증 결과, 규칙 위반이 없다고 판단되었거나
  - 발견된 문제에 대해 사용자의 명시적 판단이 완료되었을 것
- 위 조건이 충족되지 않으면 AI는 코드를 작성하지 않는다.

### 8.5 무인 실행 안전성 보장

- 본 검증 단계는 사용자가 요청 후 즉시 모니터링하지 않는 상황을 전제로 한다.
- 문서 검증을 통과하지 않은 상태에서의 자동 코드 작성은 금지된다.

## 9. 이슈(Issue)에 대한 기본 관점 및 원칙

이 프로젝트에서 이슈(Issue)는  
AI가 작업을 진행하는 과정에서 **스스로 판단할 수 없는 문제를 사용자에게 위임하기 위한 공식 기록 수단**이다.

이슈는 문제 해결을 위한 토론 공간이 아니라,  
**판단 보류 상태를 명확히 남기기 위한 로그**로 취급한다.

---

### 9.1 이슈의 목적

- 이슈는 다음과 같은 상황을 기록하기 위해 존재한다.
  - 문서 간 규칙 충돌
  - 문서 정의의 누락 또는 모호성
  - 구현을 계속하기에 판단이 필요한 설계 문제
  - 규칙 위반 가능성이 있는 요구사항

- AI는 이슈를 통해 문제를 **기록하고 위임**하되,
  임의로 문서를 수정하거나 판단을 대신하지 않는다.

---

### 9.2 이슈와 작업 진행의 관계

- 이슈가 기록되었다는 사실만으로 작업이 중단되지는 않는다.
- AI는 문제의 영향 범위를 식별하고,
  **문제가 되는 기능 또는 동작을 제외한 범위에서 작업을 계속 진행한다.**

- 이때 작업 지속을 위해:
  - 특정 기능을 제외하거나
  - 비활성화하거나
  - 최소한의 대체 동작으로 유지할 수 있다.

- 어떤 방식으로 작업을 지속했는지는 이슈를 통해 사용자에게 명확히 전달되어야 한다.

---

### 9.3 작업 중단 원칙

다음 조건 중 하나라도 충족되면,
AI는 작업을 중단하고 사용자 판단을 요청한다.

- 규칙 문서 간 충돌로 인해 올바른 동작을 결정할 수 없는 경우
- 데이터 손실 또는 보안 문제로 이어질 가능성이 있는 경우
- 프로젝트가 정상적으로 빌드 또는 테스트될 수 없는 상태가 되는 경우

---

### 9.4 이슈 규칙 문서의 위임

- 이슈의 상세 작성 규칙, 형식, 템플릿, 필드 정의는
  **`/docs/issues/` 디렉토리 내 규칙 문서에서 정의한다.**
- 본 문서는 이슈에 대한 **관점과 역할만**을 정의한다.
- 이슈 기록의 세부 형식은 본 문서의 책임 범위에 포함되지 않는다.

---

### 9.5 AI의 제한 사항

- AI는 이슈를 기록할 수 있으나,
  이슈를 근거로 문서나 규칙을 직접 수정하지 않는다.
- 이슈에 대한 최종 판단과 문서 반영은 항상 사용자의 책임이다.

---

## 0. 이 문서의 위상

이 문서는 /docs 내 최상위 규칙 문서다.
이 문서의 내용은 다른 모든 문서와 코드보다 우선한다.

이 문서의 규칙을 따르지 않는 프로젝트는
본 협업 방식의 대상이 아니다.
